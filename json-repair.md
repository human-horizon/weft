# Встроенное исправление невалидного JSON

## Контекст

Шаги weft со schema требуют от модели валидный JSON. Модель может вернуть почти корректный JSON с синтаксической ошибкой, например строковое значение без двойных кавычек. Сейчас такой ответ сразу приводит к ошибке schema validation, хотя его иногда можно автоматически исправить отдельным запросом к той же модели.

## Цель

Добавить в weft одну встроенную попытку исправить ответ после ошибки `JSON.parse`, повторно спросив ту же модель о конкретном JSON. Если исправленный JSON проходит исходную Zod-схему, шаг должен завершиться успешно.

## Что изменится

1. `src/zod-middleware.ts` — добавить ограниченный JSON-repair flow и формирование repair-промпта.
2. `src/types.ts` — расширить `AgentResult` диагностикой ошибки модели, если это потребуется для repair.
3. `src/debug.ts` — использовать существующее debug-логирование для начала, результата и ошибки repair-запроса.
4. `tests/weft.test.ts` — добавить тесты успешного repair и неуспешного repair с замоканным агентом.
5. `json-repair.md` — эта спецификация и отметки верификации.

## Детали реализации

1. В `invokeWithSchema` явно разделить два этапа:
   - `JSON.parse` извлечённого текста;
   - проверка разобранного значения через исходную Zod-схему.
2. При первой ошибке `JSON.parse` выполнить не более одной repair-попытки для текущего шага.
3. Repair-запрос отправлять через `invokeAgent` с той же моделью, параметрами thinking и сигналом отмены. Repair не должен вызывать `invokeWithSchema` и не должен запускать новый repair-рекурсивно.
4. Repair-промпт должен содержать:
   - исходный ответ модели;
   - описание ожидаемой схемы;
   - инструкцию определить, является ли текст JSON или исправимым почти-JSON;
   - требование вернуть только исправленный JSON без markdown, комментариев и пояснений;
   - требование сохранить смысл исходного ответа и структуру схемы.
5. Ответ repair пропустить через существующий `extractJson`, `JSON.parse` и исходную Zod-схему. При успехе вернуть результат без дополнительного pipeline-step.
6. Если repair не удался, продолжить существующий retry-flow. Повторный repair для того же шага не выполнять.
7. Если все попытки исчерпаны, бросить существующий `WeftSchemaValidationError`, добавив в него диагностические поля о repair-попытке и безопасно отобразив их в тексте ошибки.
8. Ошибка провайдера или таймаут repair не должны маскировать исходную ошибку ответа модели.
9. Все debug-сообщения repair писать только в stderr через `debugLog`; stdout pipeline не изменять.

## Критерии приёмки

- [x] При синтаксически невалидном JSON вызывается отдельный repair-запрос не более одного раза на шаг.
- [x] Валидный исправленный JSON, проходящий Zod-схему, возвращается как результат шага.
- [x] Repair не вызывается для валидного JSON, который не проходит только Zod-схему.
- [x] Неуспешный repair сохраняет исходную ошибку и добавляет диагностическую информацию.
- [x] Таймаут или ошибка repair не приводит к рекурсии и не маскирует исходную причину.
- [x] `npx tsc` завершается успешно.
- [x] `npx vitest run` проходит полностью: 43 теста.
- [ ] Линтер завершается без ошибок — в package.json нет lint-скрипта и в node_modules отсутствует линтер.
